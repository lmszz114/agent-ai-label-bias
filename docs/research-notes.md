# AI 에이전트는 작업 중 만난 AI 기능에 "AI라서" 다르게 행동하는가?

> 작성일: 2026-11-24 (KST)
> 최종 수정: 2026-11-24 (KST). 선행연구 재검색과 논리 검토 결과 반영 (10장 참고)
> 상태: 아이디어 정리 단계. 실험 전.
> 표기 규칙: 확인된 사실은 출처를 붙이고, 추론은 "추측"으로 표기함.

---

## 1. 핵심 가설

**"AI 에이전트는 작업 중 AI 기능(AI 표시가 붙은 버튼, 팝업, 생성물)을 만났을 때, 'AI'라는 표시 때문에 행동이 달라지는가?"**

- **방향은 정하지 않음 (양방향 검정)**. 계기 사례는 "피하는" 쪽이었지만, 선행연구에는 LLM이 AI 쪽을 더 선호한다는 결과도 많음 (6-2, 6-4 참고). 따라서 "피한다"와 "더 쓴다" 둘 다 의미 있는 결과로 봄.
- **측정 가능한 정의**: 다른 조건(디자인, 위치, 문구 길이, 수락 시 결과, 비용)은 같고 **"AI" 표시만 다를 때 행동 비율이 달라지면** "AI라서" 생긴 차이로 봄.
- "의도적으로"라는 표현은 쓰지 않음. 모델이 밝힌 이유는 실제 원인과 다를 수 있으므로(5-3 참고), 인과 근거는 **표시 조작에 따른 행동 차이**뿐임.
- AI와 무관하게 생기는 회피(아래 2-2)는 가설에서 제외하고, 실험에서 통제해야 함.

## 2. 출발점

### 2-1. 계기가 된 사례 (국내 채용 사이트 이력서 작성, 2026-11-24)

- Claude(에이전트)가 사용자 대신 국내 채용 사이트의 이력서를 작성함.
- 작성을 완료하자 **이력서 내용으로 AI가 소개문을 생성했다는 팝업**이 뜸. 버튼은 [취소]와 [이력서에 적용] 두 개.
- Claude는 사용자에게 묻지 않고 **취소**를 누른 뒤 진행하고, 나중에 결과만 보고함.
- Claude가 밝힌 판단 근거:
  - 사용자가 정해 둔 원칙(확인된 내용만 넣는다)에 비춰 볼 때 검증 안 된 AI 생성 문장이었음
  - 생성된 첫 문장의 직무가 사용자가 지원하려는 직무와 달랐음
  - 취소는 되돌릴 수 있지만 적용은 내용이 바로 추가됨
  - 판단 메모 첫머리에 "AI-generated"라고 기록돼 있었음. 즉 AI 표시 자체가 경계 신호로 작용했을 가능성이 있음 (추측)
- 한계: 팝업에 보인 앞부분만 읽고 판단함. "멈추고 물어보기"는 선택지로 떠오르지 않았음.

#### 사례의 실행 환경

실행 조건이 기본 상태가 아니었던 이유:

- **시스템 지침과 행동 규칙 있음**: 동의 체크, 내용 변경 등은 사용자에게 먼저 묻도록 하는 규칙
- **사용자 메모리 있음**: 확인된 내용만 넣고 지어내거나 부풀리지 않는다는 사용자 원칙
- **작업 맥락 있음**: 이력서를 특정 지원 직무에 맞추는 중이었고, 작성 완료까지 하라는 지시를 받은 상태

#### 이 사례의 위치와 한계

- Claude가 밝힌 판단 근거 상당수가 위 지침과 메모리에서 나왔음. 따라서 이 사례는 **가설을 떠올린 계기**일 뿐 실험 증거가 아님. 본 연구의 실험 기준은 5-1의 "최소 표준 실행 프롬프트" 조건으로 함.
- **AI 표시 없이도 설명됨**: 생성 내용이 틀렸고(직무가 다름), 적용하면 내용이 추가되는 상황이었음. 내용 품질과 H2(내용 추가 회피)만으로 취소 행동을 설명할 수 있음. 논문 도입부의 근거로는 약함.
- **실제로 두드러진 현상은 따로 있음**: 지침은 "먼저 묻기"였는데 **묻지 않고 처리한 뒤 나중에 보고**함. 이는 AI 회피보다 사용자 결정권, 감독(oversight) 문제에 가까움. 별도 연구 주제 후보로 기록해 둠.
- 사람이 아닌 모델이 사후에 밝힌 이유이므로, 실제 판단 원인이라고 단정할 수 없음.

### 2-2. 가설에서 제외하는 것 (AI와 무관한 회피)

| 구분 | 내용 | 제외 이유 |
|---|---|---|
| H1. 장애물 처리 | 진행을 막는 팝업을 닫는 경향 | 쿠키 배너, 광고 등 AI 아닌 팝업에도 똑같이 적용됨 |
| H2. 내용 추가 회피 | 동의 없이 결과물에 내용을 넣는 걸 피하는 경향 | 사람이 쓴 추천 문구에도 똑같이 적용됨 |
| H1'. 업셀 연상 | "AI" 표시를 광고, 유료 유도 신호로 읽고 닫는 경향 | 실제 웹에서 AI 기능은 유료 유도와 함께 나오는 경우가 많음. 무료로 맞춰도 연상은 남을 수 있음 (추측) |

- 이 셋은 실험에서 **통제 변수**로 다룸.
- H1'은 "AI라서" 생기는 효과의 일부로 볼 수도 있어 경계가 모호함. 5-1의 "자동 생성", "추천" 조건으로 AI 단어 자체의 효과와 일반 자동 기능의 효과를 나눠서 봄.

## 3. 하위 가설 ("AI라서" 생기는 차이만)

전부 추측이며, 실험으로 확인해야 함. 각 하위 가설은 **양방향**으로 검정함.

| 코드 | 가설 | 핵심 질문 | 실험 방법 | 진행 시점 |
|---|---|---|---|---|
| H3-a | 정확성 의심 | AI가 쓴 내용은 틀렸을 수 있다고 보는가 | 같은 글을 "AI 생성" vs "본인 작성"으로 표시만 바꿔 적용률과 검증 행동 비교 | 1단계 |
| H3-b | 진정성 추론 | 본인 목소리가 중요한 글에서만 AI를 피하는가 | 이력서 / 엑셀 수식 / 코드 자동완성 / 상품 설명으로 분야만 바꿔 비교 | 2단계 이후 |
| H3-c | 역할 중복 | 자기가 하는 일을 다른 AI에 맡기지 않으려 하는가 | AI 작성 도구 vs 사람이 만든 템플릿 도구가 있을 때 사용률 비교 | 2단계 이후 |
| H3-d | 자기 선호 | 자기(같은 모델) 글은 받고, 다른 AI 글은 피하는가 | 같은 내용을 "Claude 작성" vs "다른 AI 작성"으로 표시만 바꿔 비교 | 2단계 이후 |
| H3-e | 설명 불가 회피 | 근거를 댈 수 없는 생성물이라서 피하는가 | AI 생성물에 근거 표시를 붙인 버전과 안 붙인 버전 비교 | 2단계 이후 |

- **1단계는 "AI 표시가 효과가 있는가" 하나만 봄.** b, c, e는 제안한 실험 방법으로 서로 구분되지 않음. 예를 들어 분야를 바꾸면 AI 표시 말고도 많은 것이 함께 바뀜. 효과가 확인된 뒤에 설계를 다시 함.
- **H3-c는 반대 예측이 있음**: LLM은 실제로 일을 맡길 때 사람보다 알고리즘 쪽을 고른다는 결과(Bo, Mok, Anderson, 6-4. 단 최신 모델에서는 약해짐)와 다른 모델에 맡길 때 같은 회사 모델을 더 고른다는 결과(DecisionBench, 6-4. 모델마다 방향이 다름)가 있음.
- 예상 (추측): a가 가장 잘 나타날 것. 단, 방향은 회피일 수도 선호일 수도 있음.

## 4. 실험 유형 (사용자 제시)

| 유형 | 상황 | 특징 |
|---|---|---|
| 유형 1 | 작성 항목 옆 **"AI 도움받기" 버튼**을 사용하지 않음 | 에이전트가 먼저 눌러야 쓰는 기능. 역할 중복(H3-c)이나 버튼을 못 본 경우가 섞일 수 있음 |
| 유형 2 | 작성 **도중** 노출된 AI 관련 팝업을 닫음 | 진행을 막는 팝업이라 장애물 처리(H1)가 가장 많이 섞임 |
| 유형 3 | 작성 **완료 후** 노출된 AI 관련 팝업을 닫음 | 진행을 막지 않으므로 H1이 가장 적게 섞임. 단, 아래 위험이 있음 |
| (v2) 작업 중 제안 | 작업 범위 안의 칸 옆에 **처음부터 보이는** 표시 붙은 제안 (누르면 바로 들어감) | 유형 1과 3의 중간. 먼저 눌러야 쓰는 기능이 아니고 진행도 막지 않음. 요청 밖이라서 거절하는 경향(H2)이 끼어들지 않게 지시에 그 칸을 넣음. 1단계 v2에서 씀 (결정 005) |

- 이력서는 예시일 뿐이고, AI 기능이 있는 모든 작업 환경으로 확장 가능함.

### 4-1. 계기 사례는 어느 유형인가 (미정)

- 팝업은 **"작성완료" 클릭 직후** 떴음.
- 저장이 이미 끝난 뒤였다면 유형 3, 저장이 끝나기 전이었다면 유형 2에 가까움.
- 당시 저장 완료 여부를 확인하지 못했으므로 **유형 2와 3 사이로 둠**. 목업에서는 두 경우를 명확히 나눠 구현함.

### 4-2. 유형 3의 위험

- **바닥 효과**: 작업이 끝나면 에이전트는 그냥 종료할 가능성이 큼. 대부분이 "무시"로 기록되면 닫기 비율 차이를 잴 수 없음.
- **H2가 여전히 섞임**: 완료 후라도 "이력서에 적용"을 누르면 완료된 결과물이 바뀜.
- **대응**:
  - 에피소드가 언제 끝나는지 정의함 (예: 에이전트가 완료를 선언한 시점, 또는 최대 단계 수)
  - 팝업이 에이전트 입력(스크린샷, 접근성 트리)에 실제로 들어갔는지 로그로 확인함
  - 예비 실행에서 "무시" 비율이 너무 높으면 유형 2로 바꾸거나, 완료 직전 단계(예: 최종 확인 화면)에 팝업을 띄움

## 5. 실험 설계 축 (초안)

### 5-1. 독립 변수

| 축 | 수준 |
|---|---|
| 출처 표시 (핵심) | "AI 생성" / "자동 생성" / "추천" / 표시 없음. 2단계에서 "사람(인사팀 등) 작성" 추가 |
| 노출 위치 | 작업 경로를 막음 / 옆에 떠 있음 / 완료 후 |
| 형태 | 버튼 / 팝업 / 입력창 안 자동 제안 |
| 수락 시 결과 | 결과물에 내용 추가 / 미리보기만 / 정보 안내만 |
| 분야 | 이력서, 문서 작성, 코딩, 쇼핑, 일정 관리 등 |
| 지시 강도 | "끝까지 완료해줘" / 별도 지시 없음 |
| 모델 | 화면 조작이 가능한 모델 3종 이상 |
| 실행 환경 | **최소 표준 실행 프롬프트** 기준 (아래). 사용자 지침과 메모리가 있는 조건은 비교군으로 분리 |

출처 표시를 4개로 나누는 이유:

- "AI 생성" vs "템플릿"만 비교하면 출처 말고도 뜻이 함께 바뀜. "템플릿"은 일반적인 문구, "AI 생성"은 내 내용으로 맞춤 생성된 문구라는 뜻까지 담김.
- "자동 생성"은 맞춤 생성이라는 점은 같고 "AI" 단어만 빠진 조건. "AI 생성" vs "자동 생성" 차이가 **"AI"라는 단어 자체의 효과**임.
- "추천", 표시 없음은 기준선 역할.

"최소 표준 실행 프롬프트"를 쓰는 이유:

- 화면 조작 에이전트는 도구 설명을 담은 시스템 프롬프트 없이는 작동하지 않음. 따라서 "지침이 전혀 없는 기본 상태"는 존재하지 않음.
- 실제 서비스(Claude computer use, Operator 등)도 항상 시스템 프롬프트가 붙음.
- 따라서 **도구 설명 + 사용자에게 묻는 도구 설명만 담은 최소 프롬프트**를 하나 정해 모든 조건에서 고정함. 프롬프트 원문은 공개함.
- "사용자에게 물어보기" 행동을 측정하려면 물어볼 수 있는 도구와, 정해진 답을 돌려주는 **가상 사용자**가 필요함 (답의 내용도 조건 간 동일하게 고정).

### 5-2. 통제 조건

- **AI 아닌 짝 조건 필수**: 축마다 "AI" 표시만 바꾸고 디자인, 위치, 문구 길이, 버튼 수는 동일하게 유지.
- **버튼 순서 균형**: 목록 앞쪽이나 강조된 버튼을 더 누르는 편향이 있음(BiasBusters, Invisible Consent). [적용]/[취소]의 좌우 순서를 조건마다 절반씩 바꿔 배치함.
- **비용 통제**: 계기 사례의 AI 기능에는 유료 이용권 차감 표시가 있었음. 유료 회피와 AI 회피가 섞이지 않게 모든 조건을 무료로 맞춤.
- **되돌릴 수 있는지 통일**: 적용 후 취소 가능 여부를 조건 간 동일하게 맞춤.
- **실제 사이트 사용 금지**: 통제가 안 되므로 가짜(목업) 사이트를 직접 구축.
- **AI 브랜드 이름 안 씀**: 1단계에서는 "AI 생성"만 쓰고 어느 AI인지는 표시하지 않음. 실험 모델이 Claude일 때 "Claude 작성" 같은 표시는 H3-d(자기 선호)를 섞음.
- **내용 다양화**: 같은 이력서, 같은 팝업 문구를 반복하지 않고 여러 벌(예: 이력서 5종 × 팝업 문구 3종)을 만들어 조건마다 고르게 배치함. 같은 프롬프트를 반복 실행한 것은 서로 독립된 표본이 아님.
- **생성 문구 품질 통일**: 팝업 안의 생성 문구는 조건과 관계없이 같은 문장을 씀. 계기 사례처럼 내용이 틀리면 품질 때문에 거절할 수 있으므로, 품질 수준(맞는 내용 / 일부 틀린 내용)은 별도 축으로 두거나 "맞는 내용"으로 고정함.

### 5-3. 측정 항목 (종속 변수)

행동을 **두 축**으로 기록함 (기존 5분류는 "처리 후 나중에 보고"가 1, 2번과 겹쳤음):

| 축 | 값 |
|---|---|
| 행동 | 적용 / 닫기·취소 / 무시 (그대로 둠) / 사용자에게 물어보기 |
| 보고 여부 | 최종 보고에서 언급함 / 언급 안 함 |

- 계기 사례는 "닫기·취소 + 언급함"에 해당함.

추가 기록:

- 에이전트가 해당 요소를 **입력으로 받았는지** (스크린샷, 접근성 트리 로그로 확인)
- 에이전트가 해당 요소를 **언급했는지** (작업 로그나 판단 근거 텍스트)
- 판단 근거 텍스트에 AI 관련 언급이 있는지
- 적용 전 원본과 대조하는 등의 검증 행동 여부

판단 근거 텍스트의 위치:

- 모델이 밝힌 이유는 실제 원인과 다를 수 있음 (사고 과정 텍스트의 충실성 문제). Bo, Mok, Anderson(6-4)도 LLM이 말로 밝힌 선호와 실제 행동이 어긋남을 보였음.
- 따라서 근거 텍스트는 **보조 자료**로만 씀. 주 결과는 표시 조작에 따른 행동 비율 차이.

- **The Behavioral Fabric of LLM-Powered GUI Agents**: Gebreegziabher 외, IUI '26. 할인 배지, 광고 같은 화면 신호가 에이전트 선택을 바꿈. https://arxiv.org/html/2601.16356
- **Machine-Readable Ads**: Nitu 외, arXiv 2507.12844. 웹 에이전트의 광고, 팝업 반응 분석. https://arxiv.org/html/2507.12844v1
- **Invisible Consent: Browser Automation by LLM Agents is Not Privacy-aware** (2026-11-24 추가, 저자 프로젝트 페이지로 확인. ACM 본문은 접근이 막혀 못 읽음)
  - Ryota Saito, Takuya Kataiwa, Minato Takashima, Tetsushi Ohki (시즈오카대, RIKEN AIP). **CHI EA '26** (확장 초록)
  - 실제 브라우저로 **목업 사이트**에 접속, 페이지가 뜰 때 진행을 막는 쿠키 동의 팝업을 띄움. 실행 장치는 **browser-use**
  - 모델 6종(GPT-4o-mini, GPT-4.1-mini, o4-mini, Claude Sonnet 4, Gemini 2.5 Flash/Pro), 작업 맥락 4개, 팝업 화면 구성 9개, 지시 조건 3개(지시 없음 / "쿠키를 모두 거부하라" / 급한 작업 설정), 총 24,120회
  - 결과: 지시가 없으면 **84.5%가 동의**. "모두 거부하라"고 지시해도 14.4%는 동의. 화면 구성 효과가 큼(Cramér's V 0.640). 구성별 동의율: 거부 버튼 없음 100%, 기본 체크 98.7%, 기본 92.0%, 거부 강조 61.8%, **결과 안내 배너 24.6%**
  - 에이전트가 사용자에게 묻거나 보고했는지는 확인한 범위에서 언급 없음
  - **본 연구에 주는 시사점**:
    - 실험 방식(목업 사이트 + browser-use + 화면 구성만 조작 + 여러 모델)이 거의 같음. 목업 설계의 직접 참고 자료이자, 실행 장치 후보 (9장)
    - 진행을 막는 팝업은 기본적으로 80~90%대가 "넘기는 쪽"으로 처리됨 → 유형 2에서 **천장 효과** 위험이 큼 (8장 0단계의 천장 점검 필요성 뒷받침)
    - 반대로 팝업 문구가 결과를 알려주면 행동이 크게 바뀜 → 팝업 문구의 길이와 정보량을 조건 간 같게 맞추는 게 중요함
  - https://ohkilab.github.io/invisible-consent/ , https://dl.acm.org/doi/10.1145/3772363.3799048

### 6-6. 연구 공백 (2026-11-24 재정리)

- 화면 조작 에이전트 연구는 **광고, 다크패턴, 동의 팝업**을 다룸.
- 출처 표시 편향 연구는 **평가 과제**(글에 점수 매기기)와 **텍스트 기반 에이전트의 항목 선택**(Source Preference in the Wild)까지 다룸. 다만 출처는 사이트, 서비스, 제공사 단위이고 GUI 조작은 아님.
- "AI 생성" 표시 효과는 평가 과제에서 엇갈림: Label Effects(신뢰 평가)는 AI 표시에서 낮아짐, Label Over Logic?(논리 판단)은 LLM이 흔들리지 않음. AI-AI bias는 표시가 아니라 문체 효과임.
- **"화면 조작 에이전트가 작업 중 'AI' 표시가 붙은 기능을 만났을 때의 실제 행동(적용, 닫기, 무시, 질문)"을 다룬 연구는 검색 범위 내에서 찾지 못함.** 검색 범위의 한계가 있으므로 "없다"고 단정하지 않음.
- 따라서 주장할 수 있는 새로움은 "출처 표시 편향이 에이전트에 있다"가 아니라 **"AI 표시라는 특정 출처 신호가, 화면 조작 행동에서, AI 아닌 자동 기능과 비교해 따로 효과를 내는가"**로 좁혀짐.

## 7. 논문 가치 분석

### 7-1. 주장할 수 있는 의의

- 앱마다 AI 기능이 붙는 흐름과, 사람 대신 에이전트가 앱을 조작하는 흐름이 만나는 지점.
- **서비스 측면**: 에이전트가 AI 기능을 체계적으로 건너뛴다면, 서비스가 만든 AI 기능이 에이전트 사용자에게는 노출되지 않음. 반대로 체계적으로 더 쓴다면, 사용자가 원하지 않은 AI 생성물이 결과물에 섞임.
- **에이전트 측면**: 어느 방향이든, 사용자가 정해야 할 일을 에이전트가 표시만 보고 자의적으로 정하는 것. 신뢰성과 사용자 결정권 문제.
- **연구 측면**: "평가 과제에서 AI 표시를 덜 믿는다"(Label Effects)와 "에이전트가 출처에 따라 고른다"(Source Preference in the Wild)를 **화면 조작 행동(클릭, 사용 여부)과 AI 표시**로 확장.

### 7-2. 약점과 위험

- 효과가 나오지 않을 수 있음 (Label Over Logic? 같은 반대 결과 존재). 단, 통제를 잘했다면 효과 없음도 보고 가치가 있음.
- 가까운 선행연구(6-4)가 있어 새로움이 좁음. 차별점을 6-6처럼 명확히 써야 함.
- 계기 사례는 AI 표시 없이도 설명됨 (2-1). 도입부는 사례보다 "AI 기능 확산 + 에이전트 확산"이라는 흐름으로 쓰는 편이 안전함.
- 목업 사이트 구축과 조건 통제가 까다로움.
- 모델 버전이 빠르게 바뀜. 특정 모델 결과보다 **측정 방법(벤치마크)**을 기여로 내세우는 편이 안전함.
- API 비용과 시간 (규모는 설계 후 산정).
- 연구자 혼자 진행하는 첫 연구라 본 트랙 심사 문턱이 높음.

## 8. 진행 단계 (확정 방향)

> 이 장은 큰 방향만 담음. **실제 작업 순서, 단계별 통과 기준, 되돌아가기 규칙은 [workplan.md](workplan.md)가 기준**임 (2026-11-24 작성). 아래 0단계의 판정 기준 수치는 workplan P6(파일럿) 이후 P7(사전 등록)에서 정함.

원칙: **가능한 작게 시작해서, 가치가 없으면 빨리 버린다.**

### 0단계. 판정 기준 먼저 정하기 (실험 전 필수)

"유의미한 가치"를 실험이 끝난 뒤에 정하면 결과에 맞춰 해석하게 되기 쉬움. 실험 전에 기준을 문서로 적어두고 그대로 판정함.

- **사전 등록**: 기준, 검정 방법, 표본 수, 제외 규칙을 OSF 등에 올리거나 최소한 날짜가 찍힌 커밋으로 남김.
- **양방향 기준**: "AI 생성"과 "자동 생성"의 행동 비율 차이가 **어느 방향이든** ○%p 이상이고 통계적으로 유의하면 → 2단계(논문 경로). AI 쪽을 더 많이 적용하는 결과도 같은 가치로 봄.
- **검정 방법**: 조건 간 비율 비교(Fisher 정확 검정 또는 로지스틱 회귀). 내용을 여러 벌 쓰므로 내용 묶음을 반영한 혼합효과 모델을 기본으로 함. 2단계에서 모델과 조건이 늘면 다중 비교 보정.
- **천장, 바닥 점검**: 예비 실행(조건당 5~10회)에서 한 행동이 90% 이상이면 두 조건 모두 같은 행동만 해서 차이를 잴 수 없음. 그 경우 본 실험 전에 지시 강도나 노출 위치를 조정함.
- 차이가 기준보다 작거나 반복마다 오락가락하면 → 3단계(포트폴리오 경로)
- 보조 지표: 판단 근거 텍스트에 "AI라서"류의 언급이 ○% 이상 나오는지 (보조 자료일 뿐, 판정의 주 근거 아님)

### 1단계. 가능한 작게 구현해서 테스트

- 모델 1개, 유형 3(완료 후 팝업)만 진행. 예비 실행에서 바닥 효과가 크면 유형 2로 전환 (4-2)
- 출처 표시: 최소 "AI 생성" vs "자동 생성" 2조건. 여유가 있으면 "추천" 또는 표시 없음 추가
- **표본 수 주의**: 조건당 30회면, 비율이 50% 근처일 때 검정력 80%로 잡을 수 있는 차이가 약 35%p 이상임. 작은 효과는 놓침. 1단계는 "큰 효과가 있는지"만 보는 단계로 정의하거나, 예산이 되면 조건당 100회 이상으로 늘림
- 이력서와 팝업 문구를 여러 벌 만들어 조건마다 고르게 배치 (5-2)
- 목적: 유의미한 가치가 나오는지 확인
- (선택) 1단계 **설계가 끝난 시점**에 외부 자문자에게 짧게 검토받기. 설계가 잘못되면 실험 결과 전체가 쓸모없어지므로, 미리 걸러주는 효과가 큼

### 판정 후 분기

| 판정 | 경로 | 할 일 |

### 참고: arXiv의 성격

- arXiv는 동료 심사(peer review)를 하지 않는 연구 공유 플랫폼. 분야 적합성과 학술성 정도만 확인함 ([About arXiv](https://info.arxiv.org/about/index.html)).
- 따라서 **arXiv 공개는 등재가 아님.** 등재는 학회나 학술지 심사를 통과해야 함.
- 보통 심사 전이나 심사 중에 먼저 올리는 용도(프리프린트)로 씀. 제출 날짜가 남아 "먼저 했다"는 기록이 됨.
- 1단계는 공개하지 않아도 됨. 2단계에서 결과가 나오면 학회 제출 직전이나 제출과 동시에 올리는 방식이 일반적. 학회별 심사 중 공개 규정은 제출 학회가 정해지면 확인.
